## Problem

The company's consumer interior-design app had users but little investor interest. Realtors kept asking for the same AI staging and research tools, but wrapped in a workflow built around their clients and listings, not around one-off room makeovers.

## What I built

I proposed the pivot to realtors and built the platform alone in **1 week**. It runs on Next.js, FastAPI, and PostgreSQL. Realtors manage clients and properties in one place and chat with an AI assistant that answers from listing data, client context, web research, and PDFs they upload. The app writes buyer and seller reports as PDF or a shareable web page with the realtor's own branding, and checks listing photos and descriptions against National Association of Realtors staging guidance. A mobile page serves showings, and a workflow dashboard chains research, staging posts, and reports into **1 click**. A Chrome extension carries the user's data onto other platforms.

## Architecture

The web app talks to one FastAPI backend. Listing and client data live in PostgreSQL on Supabase, where pgvector powers search over text chunks embedded with Gemini. LangGraph runs the assistant, and a renderer turns report data into PDF and HTML. The Chrome extension calls the same API.

```
Next.js app → FastAPI → PostgreSQL (pgvector) → Gemini embeddings → LangGraph assistant → PDF / HTML reports
```

## Result

- MVP live in **1 week**, built solo
- **11** investor inquiries at one startup conference, up from **2** for the consumer product
- One of **2** B2B AI apps I build and maintain

## Troubleshooting

Problem: realtors uploaded their own PDFs and expected the assistant to answer from them. Cause: a model cannot read long documents reliably in one prompt, and each user's files must stay private. Fix: I split each PDF into chunks, turned them into vectors, and stored them in Supabase pgvector as a per-user knowledge base. Result: the assistant answers from each realtor's own documents.
